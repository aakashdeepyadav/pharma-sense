# Security and Operational Risk Register

Review at each release and after changes to hosting, network boundaries, or authentication. Items marked open require an owner and evidence before production use.

| ID | Risk | Severity | Current treatment | Required follow-up |
| --- | --- | --- | --- | --- |
| R1 | A development database password was committed in the earlier `develop` history; the current Compose setup requires an ignored root `.env` value and binds PostgreSQL to localhost. Existing initialized volumes retain their old password. | High until rotated | Fixed in the current tree; CI scans for leaked secrets and tracked env/dump files. | Treat the old value as exposed, rotate any existing volume or deployment deliberately, and never reuse it. Do not expose the local Compose service to a shared network. |
| R2 | Login throttling is process-local and can be bypassed by distributing attempts across API instances or addresses. | High for multi-instance deployment | Failed login attempts are limited to 10 per address per 15-minute window in each process; token revocation is stored as a hash in PostgreSQL. | Add shared edge/account-aware throttling and test proxy identity before scaling. |
| R3 | JWT key length is validated, but byte length cannot establish that the key was generated randomly. | High if operator chooses a guessable key | Startup rejects keys shorter than 32 bytes; documentation requires a unique high-entropy secret. | Generate and inject a random key, restrict access to it, and rehearse rotation; rotation invalidates existing sessions. |
| R4 | Reverse-proxy client identity is not configured; the process-local IP limiter may see the proxy address or be bypassed if forwarded headers are trusted incorrectly. | Medium | Express default proxy trust is not enabled. | Define trusted proxy hops and test spoofed and forwarded client addresses at the actual ingress. |
| R5 | The repository does not provide a production deployment stack, TLS termination, or evidence of backup restoration. | High | Local rehearsal steps and recovery checklist are documented. | Select a hosting platform, restrict network access, enable HTTPS, and complete a restore rehearsal with recorded evidence. |
| R6 | Browser security policy and transport headers depend on hosting configuration; CSP/HSTS are not configured by this API. | Medium | API sets frame/content-type/referrer headers. | Set and verify CSP/HSTS at the frontend/HTTPS edge; avoid HSTS until HTTPS is consistently available. |
| R7 | A development seed password was committed in prior history and may still exist in old local databases or copied builds. | High until rotated | Current seed requires `SEED_ADMIN_PASSWORD`, rejects production use, and does not print the password; the frontend no longer pre-fills it. | Treat the old value as exposed, rotate/delete seeded accounts in existing databases, and never reuse the old password. |
| R8 | Transitive dependency advisories can block releases or create pressure for unsafe forced upgrades. | Medium for release operations | Backend and frontend audits pass; `deepmerge-ts` is pinned to patched 8.0.2 through the backend npm override while Prisma remains on 6.19.3. | Review Dependabot updates with migration, generation, build, and test evidence; do not use `npm audit fix --force` without compatibility review. |
| R9 | Password-only authentication allows account takeover if a privileged user's password is compromised. | High for operational use | bcrypt password hashing, generic login failures, and login throttling are present. | Add and test MFA for privileged accounts before storing operational inventory data. |

No deployment risk is considered accepted solely because the app builds or local smoke tests pass. The release owner records accepted residual risks and an accountable owner in the release evidence.
